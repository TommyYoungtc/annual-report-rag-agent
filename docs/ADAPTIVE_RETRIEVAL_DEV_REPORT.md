# Adaptive Retrieval 开发集实验报告

## 结论

在同一套检索模型、Reranker 和受控答案器下，A（Static）、B（Always Agentic）和 C（Adaptive）在旧 Dev 的 122 道可回答题与 30 道困难无答案题上均达到 100%。C 平均使用 1.197 轮检索，B 为 2.803 轮；C 相比 B 减少 57.3% 的 Dense/BM25 查询、Reranker 调用和重排段落，并将摊销平均耗时降低 48.1%。

这不是新的盲测结论。旧 Dev 已参与开发；两个年度/季度错例也来自已经看过结果的 V2.1 Test，只能作为回归 canary。新公司的 V3 冻结测试将在候选锁之后另建。

## 实验设置

- 硬件：NVIDIA GeForce RTX 4060 Laptop GPU 8GB；
- 语料：V2.1 盲测版年报语料，共 6,831 个 Chunk；
- 可回答 Dev：122 题；
- 困难无答案 Dev：30 题；
- 已污染回归 canary：2 题，不进入聚合指标；
- Dense：微调后的 `bge-small-zh-v1.5`；
- 稀疏检索：BM25；
- 融合：BM25 权重为 3 的加权 RRF；
- Reranker：Qwen3-Reranker-0.6B；
- Planner：确定性财务查询改写器，无 LLM Token 或 API 成本；
- 最大轮数：A 为 1，B/C 为 3；困难无答案至少确认 2 轮。

三套系统共享每轮检索结果，唯一主要变量是检索控制策略。策略成本只累计其实际会执行的轮数；模型加载时间按该轮问题数摊销。

|---|---:|---:|---:|---:|---:|
| A Static RAG | 100%（122/122） | 100% | 100% | 100% | 100%（30/30） |
| B Always Agentic | 100%（122/122） | 100% | 100% | 100% | 100%（30/30） |
| C Adaptive | 100%（122/122） | 100% | 100% | 100% | 100%（30/30） |

A 在旧 Dev 已经满分，因此 B/C 不可能在这组数据上继续提升聚合准确率。本轮主要检验复杂检索是否浪费预算，以及 Verifier 能否针对已知时间粒度错误触发自我纠错。

## 预算与轨迹结果

| 系统 | 平均检索轮数 | Dense/BM25/Reranker 调用 | 重排段落 | 每个正确任务重排段落 | 平均摊销耗时 | P50 / P95 |
|---|---:|---:|---:|---:|---:|---:|
| A Static RAG | 1.000 | 152 / 152 / 152 | 1,520 | 10.00 | 2,385.83 ms | 2,485.78 / 3,495.25 ms |
| B Always Agentic | 2.803 | 426 / 426 / 426 | 4,260 | 28.03 | 5,048.50 ms | 5,057.62 / 6,737.66 ms |
| C Adaptive | 1.197 | 182 / 182 / 182 | 1,820 | 11.97 | 2,617.53 ms | 2,631.23 / 4,382.38 ms |

C 相比 B：

- 平均检索轮数从 2.803 降到 1.197，减少 57.3%；
- Reranker 调用从 426 次降到 182 次，减少 57.3%；
- 重排段落从 4,260 个降到 1,820 个，减少 57.3%；
- 平均摊销耗时从 5,048.50 ms 降到 2,617.53 ms，减少 48.1%；
- 在这组 Dev 上保持相同质量。

C 相比 A 多出的 30 次检索来自困难无答案题的第二轮确认。按“Static 已经答对/拒答正确”定义，C 的经验性不必要升级率为 19.7%，B 为 100%；这说明当前 Dev 无法证明 C 优于 A，只能证明 C 明显优于无条件多轮的 B。是否值得为可靠拒答支付这部分预算，需要由新的盲测回答。

## 年度/季度错误回归

两个 V2.1 已知错例均为“问题询问全年指标，但答案器选中了分季度表中的第一列”。A 仍错误 0/2；B 和 C 均能识别引用之前最近的“分季度主要财务指标”章节锚点，触发定向检索并排除错误时间粒度证据，最终恢复 2/2。

这两题已在开发阶段看过答案，恢复率只能说明修复机制按设计工作，不能作为新 Test 准确率或泛化证据。

## 失败消融与修正

第一次全量运行使用 Chunk 级季度标记：只要整个 Chunk 后面出现季度表，就把前面的正确年度值一并判错。该版本使 B/C 的可回答题准确率降到 90.98%（111/122），共误伤 11 题，因此未通过锁定门禁。

最终版本改为引用位置判定：先在原 Chunk 中定位答案引用，只比较该引用之前最近的年度/季度章节锚点。离线重放显示 122 道正常题的首轮误报为 0，同时两个历史季度错例仍被识别。修正后重新运行全量 Dev，所有质量门通过。

这个失败说明 Evidence Verifier 本身也需要评测；“增加检查规则”可能比不检查更差，不能只报告自我纠错成功样例。

## 本地运行与显存

完整三轮候选计算耗时 822.56 秒。Embedding 阶段峰值 PyTorch 已分配显存最高约 56.04 MiB，Reranker 阶段最高约 1,761.36 MiB。两类模型分时加载，RTX 4060 Laptop 8GB 可稳定完成。本报告中的延迟是批量实验的摊销值，不等同于在线单请求 SLA。

## 结论边界与下一步

当前可支持的结论是：在旧 Dev 已满分的前提下，无条件多轮检索没有质量收益，却显著增加预算；基于证据充分性的 C 保持了相同开发集质量，并大幅降低了相对 B 的成本。

当前不能支持“C 的泛化准确率优于 A”或“2/2 canary 是冻结测试成绩”。候选配置锁定后，应选择与开发公司零重叠的新公司，先构建并冻结标签，再对 A/B/C 只成功运行一次。
